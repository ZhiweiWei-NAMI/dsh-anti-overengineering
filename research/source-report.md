## 2. 哪些规则有直接依据，哪些需要另行判断

下面是用于归并正式规则库的候选项，ID 使用 `C` 前缀，避免与成品 preset 的最终编号混淆。触发条件针对当前准备写入的增量，不能仅见到 `try/catch`、类、接口或测试文件就报错。

| 候选 | 判断问题与触发证据 | 不应误报的情形 | 来源性质 |
|---|---|---|---|
| C01 任务范围扩张 | 新行为、重构或文件是否能对应当前明确需求？发现没有联系的新增工作才触发。 | 用户已明确要求完整交付；必要调用方同步；行为变化要求的必要说明。 | S01、S03、S06、S09 直接支持。 |
| C02 未来需求与配置膨胀 | 是否为尚不存在的场景新增选项、扩展点或分支？证据是本轮说明/代码只有“以后可能用”。 | 用户要求的阈值、频率、规则冷却本身就是当前需求；真实部署差异。 | S01、S02、S09、S13 直接支持。 |
| C03 单次抽象与过度包装 | 新共用层是否只有一处简单调用、没有实际复用，却增加理解和传参成本？ | 单一调用也能封装真实复杂性；已有接口约束；稳定的边界对象。 | S01、S02、S08、S09、S14 直接支持；不能以调用次数独自定罪。 |
| C04 假设性防御与重复校验 | 内部保证已成立，却新增无法说明实际失败路径的校验、重试、兜底。 | 用户输入、外部 API、并发不确定性、已有故障证据；必要鉴权和数据完整性。 | S01、S09 直接支持。 |
| C05 无依据兼容层 | 没有旧消费者或支持范围要求，却新增双实现、别名、过渡协议或多版本入口。 | 已确认的旧调用方、迁移承诺、官方接口版本差异。 | 从 S01/S02/S13 的范围与未来功能规则细化，非来源独立逐条原句。 |

### 一个全局判定前提

Jev 应同时看到当前任务意图、候选写入的片段/差异、必要的周边约束。给每项结论定位到文件和具体新增结构，说明它为什么对当前需求没有作用。缺少上下文时，不得把“没有看到依据”直接当成“依据不存在”。

这是本包的工程设计建议，不是上述来源中已验证的 Jev 检测算法。Jev 的分数阈值、误报率和实际干预收益需要在目标任务上测量；不能把建议的数值写成官方推荐值或已校准概率。

## 3. 对应修改提示词候选

这些是本包新写的中文提示词，供正式规则库按命中项选用。每条都要求完成原任务，避免把“反过度工程”误读为缩小用户需求或停下来询问已经授权的工作。

### C01

这次写入增加了与当前任务无关的内容：{evidence}。请撤回这些额外变更，把补丁收敛到用户要求和直接依赖它的调用方；保留完成原任务所必需的全部行为，然后继续执行。

### C02

这里为尚未需要的场景加入了配置或扩展点：{evidence}。请采用当前需求下直接可用的实现，删去没有实际使用依据的选项和分支。用户明确要求的配置仍须实现。

### C03

这个新增封装没有提供当前任务需要的复用或隔离：{evidence}。请将它简化为清楚的直接调用或局部逻辑，保留已有必要接口；不要为精简再重构周围无关代码。

### C04

这段新增防御没有对应可发生的失败路径：{evidence}。请去掉内部重复校验和猜测性的回退，按已有契约完成实现；保留外部输入校验和已有故障证据要求的处理。

### C05

这次新增兼容路径没有已知消费者或迁移要求：{evidence}。请保留当前约定的一条实现路径，移除未经要求的别名、双写或降级分支；已确认的兼容承诺继续履行。

### C06

新增性能机制引入了当前任务用不到的状态或复杂度：{evidence}。请回到满足现有规模和指标的直接实现；若当前明确指标确实需要这项机制，只保留能解释其收益的最小部分。

### C07

这次改动顺带扩展到了无关整理或说明：{evidence}。请只保留为本次行为变化必需的代码和说明更新，并清理本轮新产生的无用符号；其余文件与原有风格保持原样。

### C08

当前新增测试或复查没有解决新的具体不确定性：{evidence}。请改为验证本次变化的可观察行为，去掉实现镜像断言和无新增价值的验证步骤。满足现有验收与必要检查后继续交付。

### C09

这次写入新增了任务并不需要的工具链、依赖或临时产物：{evidence}。请优先使用已有能力完成同一目标，去掉额外脚手架；仅保留用户要求复用或本次功能确实必需的文件。

### C10

这次精简会损失行为或降低可读性：{evidence}。请恢复用户要求的功能和必要边界，使用容易理解的表达保留全部效果；简化冗余结构即可，不以行数少作为唯一标准。

## 4. 与用户要求的 Harness 流程如何衔接

这是工程原则到执行策略的映射，不替代官方 Harness 的 API 核对：

1. 用确定性的工具类型/动作识别判断是否有写入，不让 Jev 先花一次调用来猜“是不是 write”。
2. 对候选写入判断命中哪些规则。只读、搜索等轮次仍可用于轮数计数，但不应为本功能自动调用 Jev。
3. 规则本身判断“这次改动是否多余”；全局/规则冷却判断“即使命中是否应该现在提示”。两者分开，频率阈值放在 Harness 代码配置内。
4. 冷却计数须说明是模型轮、工具调用还是写入轮；同轮多次写入不能意外占用多轮冷却。
5. 同一轮多条命中合并成一条短的修正消息，避免提示词反而淹没原任务。
6. 依据是否可以在执行前修改/取消写入，准确称为“写入前重规划”或“写入后纠正”。不能把后续提示注入包装成已阻止本次写入。

上述规则需要使本功能自身保持克制。用户已请求的配置、状态持久化与必要兼容接入属于实现的一部分；不因反过度工程原则而省略。规则库也不应不断增长成大量同义条款。

## 5. 检索记录、排除与限制

主要检索词包括：`Anthropic avoid over-engineering prompt`、`Google code review complexity over-engineering`、`OpenAI Codex minimal focused changes prompt`、`Simplicity First Surgical Changes Karpathy`、`YAGNI Martin Fowler`、`Sandi Metz wrong abstraction`、`Testing Library implementation details`。先用网页搜索确定来源，再通过作者/组织官方仓库核对文件、默认分支、固定 commit 和许可。

检索包括两个网页引擎；部分精确 GitHub 文件无法由网页抓取器打开，因此改用 GitHub 只读连接器和 raw 文件下载。文件摘要使用本地原文核对，未把抓取失败当成缺少来源。

没有收录以下内容：仅重复原则的转载/镜像；没有清楚来源或许可证的“万能 system prompt”；以新增架构、边界层、测试框架作为默认答案的工作流；无法访问的 DS Karpathy 插件；受版权保护的整本设计书籍。

本资料包没有证明任何 prompt 能保证 DeepSeek 永不越界。完整文档包含相互有取舍的建议，例如 Google 的广泛测试要求和用户的精简验证偏好。正式 preset 必须按当前用户目标取舍，不能将多份文档不加区别地全量注入。
